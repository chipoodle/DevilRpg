# A5.8 — Controlador de aceptación en juego

## Decisión

Se usa un controlador de servidor, no chat ni RCON:

- `com.chipoodle.devilrpg.debug.A5TestController`.
- Se activa solo con `-Da5.scenario=smoke|s3|s5|l1|golem|guardview|terrain`.
- Vive en `src/main/java/com/chipoodle/devilrpg/debug/**`, que el build normal excluye.
- Escucha `ServerTickEvent.Post`, obtiene el `ServerPlayer` real y ejecuta en el hilo del servidor.
- **S5** exige dificultad **Normal** en el mundo desechable; en Peaceful, `Mob.checkDespawn()` elimina la oleada.

## Qué usa de producción

- `VillageManager.preGenerate(level, 0, target)` para generar la aldea real cerca del spawn.
- `VillageManager.manageNearby(...)` / `start(...)` para el asedio clásico real.
- `ServerPlayer.teleportTo(...)` y `setGameMode(CREATIVE)` para colocar al jugador.
- `VillageSavedData.isFallen(0)` para observar el terminal real.
- Para S3, `AggressiveZombieEntity.setInvulnerable(true)` y tiempo nocturno en el mundo desechable; no llama a `fallVillage` ni fuerza el resultado.

## Salida

- `result.json` con run, escenario, semilla, tick, centro, jugador, precondiciones, oleada, caídos, estado y ventana post-terminal.
- `controller.log` legible.
- El servidor se detiene solo al terminar.

## Lanzamiento

1. Generar un mundo desechable con `runServer` y un `init.gradle` que fije `gameDirectory`.
2. Copiar el mundo a `game/saves/<nivel>`.
3. Escribir `game/options.txt` con `pauseOnLostFocus:false`, `onboardAccessibility:false`,
   `skipMultiplayerWarning:true` y `tutorialStep:none`.
4. `runClient -Pa2nDiagnostics=true -Pa4nLab=true` con `-Da5.scenario=...`, `-Da5.run=...`, `-Da5.output=...`.
5. Usar `build/a5-closure/run-a5.ps1`: espera `result.json`, cierra la ventana del cliente y, si no sale en el plazo
   acotado, termina solo el JVM de ese `quickPlaySingleplayer`. Escribe `shutdown.json`.
6. No hace falta teclado, ratón, chat ni RCON.

## Hands-off execution contract (26-oct-2026)

The launcher must be fully unattended:

- no clicks, menu dismissal, keyboard, chat, or RCON;
- no foreground/focus requirement; `options.txt` must contain
  `pauseOnLostFocus:false`, `onboardAccessibility:false`,
  `skipMultiplayerWarning:true`, and `tutorialStep:none`;
- `a5.output` is resolved to an absolute path before launch, so `result.json`
  is written to the requested output root;
- result discovery accepts either the root or a nested result file, then
  validates JSON and only accepts `PASS`, `FAIL`, or `BLOCKED`;
- the launcher waits for the real result, closes/terminates only that test
  client, copies a discovered nested result to the root, writes `shutdown.json`,
  and exits 0 only for a clean PASS;
- missing, malformed, non-PASS, or unclean termination exits nonzero.

Run the script-level self-test before changing the launcher:

```powershell
.\build\a5-closure\run-a5.ps1 -SelfTest
```

**Regression warning:** do not replace this workflow with an interactive
client flow, and do not reintroduce relative `a5.output` paths. The 26-oct-2026
regression was caused by a relative output path plus result-existence-only
validation; recovery PASS was written under the client game directory and the
launcher timed out.

## Automation regression repair (26-oct-2026)

The launcher now resolves `a5.output` absolutely, discovers root or nested `result.json`, validates the JSON
result, accepts only PASS as launcher success, enforces headless client options (`pauseOnLostFocus:false`,
`onboardAccessibility:false`, `skipMultiplayerWarning:true`, `tutorialStep:none`), and terminates all matching
test clients. Self-test covers root/nested/invalid/missing results. A short smoke run passed with self-exit and
clean=True. Graphical focus-switch independence remains unverified.

Correction: the verified smoke artifact is `automation-smoke-20261026-03`
(PASS, `close-main-window`, `clean=True`, exit 0), not the earlier self-exit
smoke. A stale-result race was also fixed by archiving pre-existing results.

## Historical focus contract (read before adding focus automation)

The pre-existing A5 automation (`a5.9-fix-20261020-1300/A5.9-FIX-report.md`)
documented `pauseOnLostFocus:false` plus `CloseMainWindow` and result polling. It
did **not** document any `SetForegroundWindow`, `AttachThreadInput`, or automatic
Minecraft→Chrome handoff. Focus independence meant the integrated server kept
ticking when the user changed windows; it did not mean the automation could
change foreground ownership.

Do not add focus-stealing APIs or a new launcher architecture to satisfy a
handoff that the historical workflow never provided. Keep the isolated
`options.txt` headless keys and the existing result/shutdown lifecycle.
